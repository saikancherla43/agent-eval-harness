# Agent Evals & Observability Harness

A lightweight, framework-agnostic eval harness + structured trace logger for AI agents. Define scripted scenarios, run any agent against them, get per-run traces and aggregate metrics — the minimum viable setup for answering "is my agent actually working?" before it reaches production.

## The problem

AI agents fail silently in production. A tool starts erroring, the model misreads a qualifier, answers drift from retrieved sources — and without evals and traces, nobody notices until a customer complains. Teams either buy a heavyweight platform on day one or (more often) ship with nothing. This project is the middle path: a small harness you can read in an afternoon, adapt in a day, and grow into Langfuse/Datadog later.

## What was built

- **`tracer.py`** — structured trace logging. Every run records ordered steps with `{step_id, type (reason/tool_call/observation/final), tool_name, latency_ms (measured with `time.perf_counter`), tokens_in/out (whitespace tokenizer, documented as approximate), error, timestamp}`. Traces persist as JSONL — one JSON object per run, trivially shippable to any observability backend.
- **`harness.py`** — runs N scripted scenarios against any agent callable with signature `agent_fn(scenario, tracer) -> str`. Measures end-to-end latency around the agent call and scores success per scenario.
- **`metrics.py`** — computes from traces: task success rate, mean/median end-to-end latency, mean steps per task, tool-call error rate, total tokens, and a groundedness check: the fraction of final answers whose key claims appear as substrings in tool observations. **Documented honestly as a heuristic proxy for faithfulness, not a judge model** — see "What the numbers actually say" below.
- **`report.py`** — generates `report.md` (per-scenario table) and `results.json` from a run.
- **`mock_agent.py`** — a deterministic stand-in agent with three scripted tools (`search_docs`, `get_weather`, `calculator`) and a rule-based policy, so the harness has something real to measure. It deliberately contains one naive bug (price extraction ignores billing-period qualifiers) so the eval has a genuine failure to catch.
- **`scenarios.json`** — 8 scenarios with expected answers, covering docs QA, tool math, tool errors, and one trick question.

No dependencies, no API keys, no network calls. Python 3.10+ stdlib only.

## Architecture

```
scenarios.json ──▶ harness.py ──▶ agent_fn(scenario, tracer)
                                          │  reason / tool_call /
                       ┌──────────────────┘  observation / final steps
                       ▼
                 traces.jsonl ──▶ metrics.py ──▶ report.py ──▶ report.md + results.json
```

## How to run

```bash
python evals/run_evals.py
# Ran 8 scenarios against mock_agent.
#   success rate:      87.50% (7/8)
#   ...
# Wrote traces.jsonl, report.md, results.json
```

Swap in a real agent by passing a different callable to `run_harness` — anything that takes `(scenario, tracer)` and returns a string.

## Eval results (measured, not estimated)

From `results.json`, generated by `evals/run_evals.py` on the 8-scenario set:

| Metric | Value |
|---|---|
| Task success rate | **87.50%** (7/8) |
| Mean / median end-to-end latency | **48.1 ms** / 50.4 ms |
| Mean steps per task | **4.00** |
| Tool-call error rate | **12.50%** (1/8) |
| Groundedness (heuristic) | **62.50%** (5/8) |
| Total tokens in/out (approx) | 174 / 142 |

### What the numbers actually say

- **The eval caught a real bug.** `pricing-pro-year` ("How much does the Pro plan cost per year?") fails: the mock's price extractor returns the *monthly* price because it ignores the "per year" qualifier. That's exactly the class of silent agent failure this harness exists to surface.
- **The tool-error path works.** `weather-unknown` (Atlantis) raises in `get_weather`, the error is recorded on the trace, and the agent degrades gracefully — counted as a success with 1 tool error.
- **The groundedness heuristic shows its own limits — and that's the point.** The 3 misses are all limitations of substring-overlap as a faithfulness check, not unfaithful answers: the two arithmetic answers (`36.0`, `12.0`) normalize into fragments too short to match, and the graceful-error reply contains apology words ("sorry", "couldn't") that never appear in the error observation. A substring heuristic can't do semantic entailment. This is precisely why production setups replace this check with an LLM judge — listed below as the first recommended upgrade.

## How a client would adapt this

1. **Plug in their agent.** Replace `mock_agent` with their LangChain/LlamaIndex/custom agent — the harness only needs a `(scenario, tracer)` callable. Keep their existing tools; wrap each call with `tracer.tool_call()` for timed, token-counted traces.
2. **Add an LLM judge.** Replace the substring groundedness check with a judge model call (e.g., "does this answer follow from these observations?"), and swap substring success checks for rubric grading on open-ended tasks.
3. **Ship traces to Langfuse/Datadog.** `traces.jsonl` is already one-JSON-per-run — add a sink that POSTs each run to Langfuse or logs to Datadog, and the per-run latency/error/token fields become dashboards and alerts.
4. **Grow the scenario set.** 8 scenarios catch regressions; 50–100 versioned scenarios become a CI gate that runs on every prompt or model change.

## Honest limitations

- The mock agent is scripted, not an LLM — it stands in for agent *plumbing* (routing, tool errors, trace shape), not model behavior.
- Token counts are whitespace-based approximations, fine for relative cost comparisons, not for billing.
- Groundedness here is word overlap, not entailment (see above).
- Latencies use fixed simulated tool sleeps, so they're reproducible rather than realistic.
